# Правила работы с репозиторием

## Структура проекта

Проект на C++20 содержит реализации структур данных, консольные демонстрации и GUI на Qt 6. Точка входа консольных демонстраций — `main.cpp`, графического приложения — `GUI/source/main.cpp`. Деревья ЛР-1 и их тесты находятся в `FirstLab/headers/` и `FirstLab/tests/`. Остальные структуры и их тесты находятся в `DataStructures/` и `DataStructures/tests/`. Индексы ЛР-2 находятся в `SecondLab/include/` и `SecondLab/source/`. Умные указатели находятся в `SmartPointers/include/`, их тесты — в `SmartPointers/tests/`. Интерфейс и сервисы находятся в `GUI/include/` и `GUI/source/`, тесты интерфейса — в `GUI/tests/`. Алгоритмы поиска кратчайшего пути ЛР-3 находятся в `ThirdLab/headers`, их тесты — в `ThirdLab/tests/`. Задания находятся в `SecondLab/docs/` и `ThirdLab/docs/`, изображения — в `DataStructures/docs/img/`.

## Изменения в ЛР-1

Создавайте, редактируйте, переименовывайте, перемещайте и удаляйте файлы ЛР-1 только по прямой просьбе пользователя об изменении ЛР-1 или с его явного разрешения. Правило распространяется на весь каталог `FirstLab/` и на файлы за его пределами, посвящённые ЛР-1, включая GUI деревьев и документацию. Общая задача по репозиторию сама по себе такого разрешения не даёт.

## Дизайн учебных работ

Перед реализацией подготовьте дизайн по требованиям преподавателя из локального файла `TEMPLATE.md`. Пример оформления приведён в [дизайне умных указателей](SmartPointers/docs/specafication/Дизайн-Умных-Указателей.md).

## Интерпретатор MiniLang

Учебный интерпретатор на C++20 находится в `Interpreter/` и разрабатывается по образцу Java-проекта MiniLang. Заголовки находятся в `Interpreter/headers/`, реализации — в `Interpreter/sources/`, состояния и события лексера — в `Interpreter/enums/`.

- `Lexer::tokenize` преобразует исходный текст в собственный `Array<Token>` с завершающим `EndOfFile`. Лексер использует `StateMachine<LexerState, LexerEvent>` из ЛР-3. Токен хранит тип и исходную лексему. Лексема строки включает кавычки. Правила для ключевых слов, строк, операторов и переводов строк описаны в спецификации.
- `Parser::parse` разбирает токены рекурсивным спуском и возвращает `Array<UniquePtr<ast::Statement>>`. Узлы инструкций — `Remember`, `Print`, `When`, `RepeatWhile` и `For`. Блочные узлы владеют списками вложенных инструкций, а выражения хранятся в `ast::ExpressionTree` на основе `BinaryTreeBase`. Узлы AST поддерживают `accept` и интерфейсы `ast::ExprVisitor` и `ast::StatementVisitor`.
- `Interpreter::execute` обходит AST через оба посетителя и пишет результат в переданный поток. Значение выражения имеет тип `double`, `bool` или `std::string`. Промежуточный результат вычисления хранится в `Optional<Value>`. Каждый запуск начинается с пустого окружения.
- `minilang::Environment` хранит общие переменные в `Map<std::string, Value>`, а локальные таблицы активных `for` — через `Array<Variables*>`. Поиск имени начинается во внутренней области, присваивание обновляет ближайшее видимое имя. Счётчик `for` живёт в пределах цикла, а новые имена из `remember` попадают в общую таблицу.
- `MiniLangCpp` запускает программы из файла. Точка входа — `Interpreter/main.cpp`, пример — `Interpreter/examples/main.mini`. `MiniLangGui` из `GUI/source/MiniLangGui.cpp` показывает токены, AST, трассу и вывод программы. Для пошагового выполнения GUI использует `Interpreter::Observer`, который получает события вызовов и вычисленные значения.
- CLI, GUI и тесты используют библиотеку `MiniLangCore`. Тесты лексера, парсера, дерева выражений и исполнителя находятся в `Interpreter/tests/` и собираются в цель `InterpreterTests`. `MiniLangCliTests` отдельно проверяет запуск бинарника через CMake-сценарий. Обе группы можно выбрать в CTest по метке `Interpreter`.

Перед продолжением работы изучите [документацию MiniLang](Interpreter/docs/README.md).

- [Дизайн](Interpreter/docs/design.md) — постановка задачи, архитектура и функциональные требования к интерпретатору и GUI.
- [Спецификация](Interpreter/docs/specification.md) — правила лексики, грамматика EBNF, семантика и ошибки.
- [Архитектура](Interpreter/docs/architecture.md) — лексер, парсер, AST, окружение, исполнитель и трассировка.
- [CLI MiniLangCpp](README.md#обновление-команды-mini) — сборка, установка и запуск.
- [Расширение языка](Interpreter/docs/extending-language.md) — пример добавления оператора и порядок работы с новыми узлами AST.
- [План реализации](Interpreter/docs/implementation-plan.md) — открытые задачи и будущие проверки.

Используйте собственные структуры данных проекта. `Array::push_back` поддерживает некопируемые элементы с присваиванием перемещением без исключений, включая `UniquePtr`. Копируемые элементы сохраняют прежнюю ветку копирования. `Stack::push` принимает копируемые lvalue и перемещаемые rvalue, а `top` возвращает ссылку на вершину.

## Сборка и запуск

Нужны компилятор C++20 и CMake 3.20 или новее; для GUI дополнительно нужны Qt 6 Widgets и Concurrent. GoogleTest используется из системы или загружается CMake автоматически. Выполняйте команды из корня проекта:

```bash
cmake -S . -B /tmp/ds-build -DCMAKE_BUILD_TYPE=Release -DBUILD_GUI=ON
cmake --build /tmp/ds-build --parallel 2
ctest --test-dir /tmp/ds-build --output-on-failure
/tmp/ds-build/DataStructuresGui
```

Для консольной версии запускайте `/tmp/ds-build/DataStructures`. Если GUI не нужен, задайте `-DBUILD_GUI=OFF`. Для интерактивного GUI нужна графическая сессия; тесты интерфейса CTest запускает через Qt offscreen.

Для сборки только MiniLangCpp без Qt и GoogleTest:

```bash
cmake -S . -B /tmp/ds-build -DCMAKE_BUILD_TYPE=Release -DBUILD_GUI=OFF -DBUILD_TESTING=OFF
cmake --build /tmp/ds-build --target MiniLangCpp --parallel 2
/tmp/ds-build/MiniLangCpp Interpreter/examples/main.mini
```

Для запуска CTest включите `-DBUILD_TESTING=ON` (значение по умолчанию), выполните полную сборку и команды CTest выше. При `BUILD_TESTING=OFF` GoogleTest не ищется и не загружается.

## Стиль и именование

Используйте C++20, отступ в два пробела, открывающую скобку на строке объявления и явные подключения стандартных заголовков. Определения шаблонов храните в соответствующих `.tpp`. Для типов используйте PascalCase, для функций и переменных — lower camelCase. Давайте тестам `TEST` содержательные имена и размещайте их в `<Модуль>/tests/`. Следуйте соседнему коду; форматтер и линтер не настроены.

Комментарии к коду пишите на русском языке в стиле автора проекта: кратко, прямо и без лишней воды. Один комментарий — 1–2 предложения; объясняйте назначение, причину решения или ограничение, не пересказывая очевидный код. Имена типов, технические идентификаторы и служебные директивы IDE сохраняйте в исходном виде.

Сохраняйте авторские переносы аргументов. Если список в фигурных скобках вынесен на отдельную строку, допустимо начать его с первого столбца, как в вызовах `parseBinaryChain` в `Interpreter`.

## Тестирование

Добавляйте GoogleTest-тесты в соответствующий подкаталог `tests/`, новые исходники перечисляйте в `CMakeLists.txt`. Проверяйте обычные случаи, граничные условия и некорректный ввод. Выполняйте сборку и CTest командами выше; сообщайте фактические результаты и пропущенные проверки. Не запускайте бинарники, собранные для другой операционной системы.

## Коммиты и pull request

Пишите короткие русские заголовки коммитов, описывающие действие, например `Добавил тесты ...`. В pull request опишите поведение и затронутые модули, укажите связанные задачи и результаты сборки и тестов. Скриншоты добавляйте для изменений интерфейса или бенчмарков.

## Создаваемые файлы и конфигурация

Новые файлы в `DataStructures`, `Interpreter` и `GUI` добавляйте в Git через `git add`, чтобы они не оставались неотслеживаемыми.

Не коммитьте настройки IDE, бинарники, кеши CMake и каталоги сборки: `.idea/`, `cmake-build-debug/`, `.build-*/`. Для проверок собирайте проект в `/tmp/ds-build`. Не добавляйте секреты и конфигурацию конкретного компьютера.
