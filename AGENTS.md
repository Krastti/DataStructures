# Правила работы с репозиторием

## Структура проекта

Проект на C++20 содержит реализации структур данных, консольные демонстрации и GUI на Qt 6. Точка входа консольных демонстраций — `main.cpp`, графического приложения — `GUI/source/main.cpp`. Структуры и их тесты находятся в `DataStructures/` и `DataStructures/tests/`. Индексы ЛР-2 находятся в `SecondLab/include/` и `SecondLab/source/`. Умные указатели находятся в `SmartPointers/include/`, их тесты — в `SmartPointers/tests/`. Интерфейс и сервисы находятся в `GUI/include/` и `GUI/source/`, тесты интерфейса — в `GUI/tests/`. Алгоритмы поиска кратчайшего пути ЛР-3 находятся в `ThirdLab/include/`, их тесты — в `ThirdLab/tests/`. Задания находятся в `SecondLab/docs/` и `ThirdLab/docs/`, изображения — в `DataStructures/docs/img/`.

## Интерпретатор MiniLang

Учебный интерпретатор на C++20 находится в `Interpreter`: заголовки — в `headers/`, реализации — в `sources/`, точка входа CLI — `Interpreter/main.cpp`. Он разрабатывается по образцу Java-проекта MiniLang. Текущее состояние:

- В `Interpreter` определены `TokenType` и `Token` с полями `type` и `lexeme`. Координаты `line` и `column` отложены для будущей диагностики.
- В `Interpreter` и `Interpreter` реализован `Lexer::tokenize`, возвращающий собственный `Array<Token>`. Лексер распознаёт `remember`, `print`, целочисленные литералы, латинские идентификаторы, арифметические операторы и сравнения, скобки, LF/CRLF и EOF.
- Строковые литералы распознаются как `String`, лексема сохраняет обе кавычки. Пустые строки разрешены; экранирование и многострочные строки не поддерживаются. Для отсутствующего типа двухсимвольного оператора используется собственный `Optional<TokenType>`.
- В `Interpreter` и `Interpreter` реализован парсер рекурсивного спуска. Узлы AST объявлены в `headers/expressions.h` и `headers/statements.h`, их конструкторы и `accept` — в `sources/ast.cpp`. Типы AST находятся в пространстве имён `ast`: `NumberLiteral`, `StringLiteral`, `Identifier`, `Binary`, `Remember`, `Print`. Результат `parse` — `Array<UniquePtr<ast::Statement>>`. Каждая инструкция владеет выражением через `ast::ExpressionTree`, который использует общую с `BinaryTree` основу `BinaryTreeBase`. Парсер учитывает приоритеты, скобки и левую ассоциативность, проверяет границы инструкций и EOF. Строковые лексемы сохраняют кавычки; вычисления и проверка типов выполняются исполнителем.
- Узлы AST поддерживают `accept` и интерфейсы `ast::ExprVisitor` и `ast::StatementVisitor` из `headers/visitors.h`. Обработчики принимают константные узлы и возвращают `void`; обход дочерних узлов задаёт посетитель.
- В `Interpreter` и `Interpreter` реализован `Interpreter` через оба посетителя. Он выполняет `remember` и `print`, вычисляет числовые операции и сравнения, сохраняет и выводит строки; переменные хранятся в собственном `Map`, промежуточный результат — в `Optional`. Каждый запуск получает пустую таблицу переменных. CLI `MiniLangCpp` запускает `.mini`-файлы; пример — `Interpreter`.
- Тесты лексера, парсера и исполнителя находятся в `Interpreter/tests/` и подключены к цели `UnitTests` в CMake. Общие исходники `sources/lexer.cpp`, `sources/parser.cpp`, `sources/ast.cpp`, `sources/expressionTree.cpp` и `sources/interpreter.cpp` собираются в `MiniLangCore`, с которой связаны CLI и тесты. `MiniLangCliTests` проверяет запуск бинарника через CMake-сценарий.

Перед продолжением работы изучите [документацию MiniLang](Interpreter/docs/README.md).

- [Спецификация](Interpreter/docs/specification.md) — правила лексики, грамматика EBNF, семантика и ошибки.
- [Архитектура](Interpreter/docs/architecture.md) — лексер, парсер, AST, владение узлами и исполнитель.
- [CLI MiniLangCpp](Interpreter/docs/cli.md) — сборка, установка, запуск и проверка.
- [Расширение языка](Interpreter/docs/extending-language.md) — пример добавления оператора и порядок работы с новыми узлами AST.
- [План реализации](Interpreter/docs/implementation-plan.md) — открытые задачи и будущие проверки.

Используйте собственные структуры данных проекта. Для будущего стека вызовов предусмотрен `Stack<CallFrame>`. Перед его применением нужны возврат ссылок из `top` и перемещение некопируемых кадров через `push`. `Array::push_back` поддерживает некопируемые элементы с присваиванием перемещением без исключений, включая `UniquePtr`. Копируемые элементы сохраняют прежнюю ветку копирования.

## Сборка и запуск

Нужны компилятор C++20 и CMake 3.20 или новее; для GUI дополнительно нужны Qt 6 Widgets и Concurrent. GoogleTest используется из системы или загружается CMake автоматически. Выполняйте команды из корня проекта:

```bash
cmake -S . -B /tmp/ds-build -DCMAKE_BUILD_TYPE=Release -DBUILD_GUI=ON
cmake --build /tmp/ds-build --parallel 2
ctest --test-dir /tmp/ds-build --output-on-failure
/tmp/ds-build/DataStructuresGui
```

Для консольной версии запускайте `/tmp/ds-build/DataStructures`. Если GUI не нужен, задайте `-DBUILD_GUI=OFF`. Для интерактивного GUI нужна графическая сессия; тесты интерфейса CTest запускает через Qt offscreen.

Для сборки только MiniLangCpp без Qt и GoogleTest:

```bash
cmake -S . -B /tmp/ds-build -DCMAKE_BUILD_TYPE=Release -DBUILD_GUI=OFF -DBUILD_TESTING=OFF
cmake --build /tmp/ds-build --target MiniLangCpp --parallel 2
/tmp/ds-build/MiniLangCpp Interpreter/examples/main.mini
```

Для запуска CTest включите `-DBUILD_TESTING=ON` (значение по умолчанию), выполните полную сборку и команды CTest выше. При `BUILD_TESTING=OFF` GoogleTest не ищется и не загружается.

## Стиль и именование

Используйте C++20, отступ в два пробела, открывающую скобку на строке объявления и явные подключения стандартных заголовков. Определения шаблонов храните в соответствующих `.tpp`. Для типов используйте PascalCase, для функций и переменных — lower camelCase. Давайте тестам `TEST` содержательные имена и размещайте их в `<Модуль>/tests/`. Следуйте соседнему коду; форматтер и линтер не настроены.

Комментарии к коду пишите на русском языке в стиле автора проекта: кратко, прямо и без лишней воды. Один комментарий — 1–2 предложения; объясняйте назначение, причину решения или ограничение, не пересказывая очевидный код. Имена типов, технические идентификаторы и служебные директивы IDE сохраняйте в исходном виде.

Сохраняйте авторские переносы аргументов. Если список в фигурных скобках вынесен на отдельную строку, допустимо начать его с первого столбца, как в вызовах `parseBinaryChain` в `Interpreter`.

## Тестирование

Добавляйте GoogleTest-тесты в соответствующий подкаталог `tests/`, новые исходники перечисляйте в `CMakeLists.txt`. Проверяйте обычные случаи, граничные условия и некорректный ввод. Выполняйте сборку и CTest командами выше; сообщайте фактические результаты и пропущенные проверки. Не запускайте бинарники, собранные для другой операционной системы.

## Коммиты и pull request

Пишите короткие русские заголовки коммитов, описывающие действие, например `Добавил тесты ...`. В pull request опишите поведение и затронутые модули, укажите связанные задачи и результаты сборки и тестов. Скриншоты добавляйте для изменений интерфейса или бенчмарков.

## Создаваемые файлы и конфигурация

Новые файлы в `DataStructures`, `Interpreter` и `GUI` добавляйте в Git через `git add`, чтобы они не оставались неотслеживаемыми.

Не коммитьте настройки IDE, бинарники, кеши CMake и каталоги сборки: `.idea/`, `cmake-build-debug/`, `.build-*/`. Для проверок собирайте проект в `/tmp/ds-build`. Не добавляйте секреты и конфигурацию конкретного компьютера.
