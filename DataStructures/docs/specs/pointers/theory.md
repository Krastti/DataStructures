# Умные указатели: шпаргалка

## Основные понятия

- **Указатель** — значение, позволяющее обратиться к объекту по адресу.
- **Владелец** — тот, кто отвечает за освобождение ресурса.
- **Наблюдатель** — использует объект, но не управляет его временем жизни.
- **Время жизни** — промежуток между созданием объекта и его уничтожением.
- **Утечка** — ресурс остаётся выделенным, хотя освободить его уже некому.
- **Висячий указатель** — хранит адрес объекта, время жизни которого закончилось.
- **Двойное освобождение** — повторное удаление одного ресурса.

Сырой `T*` сам по себе не сообщает, кто владеет объектом. Умный указатель выражает владение и связывает освобождение с собственным временем жизни.

## RAII

**RAII** — ресурс принадлежит объекту, а деструктор этого объекта освобождает ресурс. При обычном выходе из области видимости и при раскрутке стека из-за исключения вызывается деструктор владельца.

```cpp
void example() {
  UniquePtr<int> value(new int(42));
  // Работа с *value.
} // Деструктор value вызывает delete.
```

Ручной `delete` после такого владения не нужен. Он создал бы риск повторного удаления.

## Единоличное владение

У `UniquePtr` один владелец. Копирование запрещено, поскольку два независимых владельца одного адреса попытались бы удалить его дважды.

```cpp
UniquePtr<int> first(new int(42));
UniquePtr<int> second(std::move(first));
// first пуст, second владеет объектом.
```

`std::move` сам ничего не переносит. Он позволяет выбрать перемещающий конструктор или оператор присваивания; уже они забирают адрес и обнуляют источник.

```text
До:     first → объект       second пуст
После:  first пуст          second → объект
```

Передача `UniquePtr` по значению означает передачу владения. Для доступа без передачи обычно достаточно ссылки на объект или сырого указателя-наблюдателя.

## Совместное владение

Все копии `SharedPtr` одной группы ссылаются на общий блок:

```text
first  ─┐
        ├→ [адрес объекта, число владельцев: 2] → объект
second ─┘
```

| Действие | Изменение счётчика |
|---|---|
| Создание из ненулевого сырого адреса | Новый блок со значением 1 |
| Копирование | Увеличение на 1 |
| Перемещение в новый экземпляр | Число владельцев не меняется |
| Уничтожение или `reset()` владельца | Уменьшение на 1 |
| Переход к 0 | Удаление объекта и блока |

При присваивании учитываются две группы: получатель отказывается от прежней доли владения и принимает новую. Если старая группа потеряла последнего владельца, её ресурс удаляется.

```cpp
SharedPtr<int> first(new int(42));
auto second = first; // Два владельца одного блока.
first.reset();      // second остаётся единственным владельцем.
```

Счётчик считает владельцев, а не сырые указатели и ссылки на объект. Получение адреса через `get()` не продлевает время жизни.

## get, release и reset

| Операция | Возвращает адрес | Опустошает владельца | Освобождает ресурс |
|---|---|---|---|
| `get()` | Да | Нет | Нет |
| `UniquePtr::release()` | Да | Да | Нет |
| `reset()` | Нет | Да | У `UniquePtr` сразу, у `SharedPtr` при последнем владельце |
| `reset(newPtr)` | Нет | Заменяет владение | Прежний ресурс по тем же правилам |

```cpp
UniquePtr<int> owner(new int(42));
int* observer = owner.get();  // Владелец всё ещё owner.
int* raw = owner.release();  // Теперь за удаление отвечает вызывающий код.
delete raw;
// observer тоже стал висячим: его нельзя разыменовывать.
```

У `SharedPtr` нет `release()`: ресурс может принадлежать другим владельцам.

## Объект и массив

```cpp
UniquePtr<int> object(new int(42));
UniquePtr<int[]> array(new int[3]{1, 2, 3});
```

Для объекта нужен `delete`, для массива — `delete[]`. Во втором случае уничтожаются все элементы. Несоответствие формы выделения и удаления вызывает неопределённое поведение.

В проекте отдельные специализации дают разные интерфейсы: у объекта есть `*` и `->`, у массива — `[]`. Границы массива не проверяются. Даже при нулевой длине массива адрес не обязан быть нулевым; проверка владельца на пустоту не определяет число элементов.

## Наследование и виртуальный деструктор

При удалении производного объекта через базовый указатель в поддерживаемой проектом модели нужен виртуальный деструктор базы:

```cpp
struct Base {
  virtual ~Base() = default;
};

struct Derived : Base {};

UniquePtr<Base> owner(new Derived);
```

Виртуальный вызов обеспечивает уничтожение производной части и базовых частей объекта. Это важно и при множественном наследовании, когда адрес базовой части может отличаться от адреса всего объекта.

Чтобы увидеть порядок вызовов, можно явно определить деструкторы:

```cpp
#include <iostream>

class Base {
public:
  virtual ~Base() {
    std::cout << "Удаление Base\n";
  }
};

class Derived : public Base {
public:
  ~Derived() override {
    std::cout << "Удаление Derived\n";
  }
};

void example() {
  Base* pointer = new Derived;
  delete pointer;
}
```

Сначала выводится `Удаление Derived`, затем `Удаление Base`: уничтожается производная часть, после неё — базовая. Без виртуального деструктора `Base` такое удаление вызывает неопределённое поведение; ресурсы производной части могут остаться неосвобождёнными.

Если у базы нет собственной логики очистки, достаточно `virtual ~Base() = default;`. Деструктор производного класса тоже становится виртуальным. Слово `override` необязательно, но позволяет компилятору проверить, что деструктор действительно переопределяет виртуальный деструктор базы.

В реализации проекта исходный тип не запоминается: удаление выполняется через хранимый `T*`. Поэтому приём производного типа без виртуального деструктора базы запрещается при компиляции. Заранее выполненное приведение к `Base*` скрывает исходный тип от проверки и не делает опасное удаление корректным.

Для массивов правило строже: `Derived[]` нельзя удалять как `Base[]` даже при виртуальном деструкторе. Элементы могут иметь разные размеры; работа с массивом базового типа не описывает размещение массива производного типа.

## Константность

```cpp
const UniquePtr<int> fixedOwner(new int(1));
*fixedOwner = 2; // Объект изменять можно, состояние владельца — нельзя.

UniquePtr<const int> fixedValue(new int(1));
// *fixedValue = 2; // Объект изменять нельзя.
```

Константность владельца и константность управляемого объекта — разные свойства. Для `SharedPtr` правило то же.

## Присваивание через временного владельца

Опасный порядок: сначала удалить прежний объект получателя, затем прочитать источник. Источник может быть полем этого объекта:

```cpp
root = std::move(root->child);
```

В проекте используется следующий порядок:

1. Создать временного владельца из источника.
2. Обменять состояния временного владельца и получателя через `swap()`.
3. При уничтожении временного владельца освободить прежний ресурс получателя.

Так источник обрабатывается до удаления содержащего его объекта. В `SharedPtr::reset(newPtr)` создание временного владельца также сохраняет прежнее состояние, если выделение нового блока завершится исключением.

## Атомарный счётчик и потоки

Атомарность делает изменение общего счётчика неделимым: параллельные операции разных владельцев не теряют увеличения и уменьшения.

Она не защищает поля управляемого объекта и не разрешает одновременно менять один и тот же экземпляр `SharedPtr` без синхронизации. `use_count() == 1` само по себе не заменяет правила синхронизации программы.

## Циклы владения

Если объект A владеет B через `SharedPtr`, а B владеет A, оба счётчика могут остаться ненулевыми после исчезновения внешних владельцев. Деструкторы не запустятся, цикл сохранит ресурсы.

Обычный способ избежать цикла — сделать обратную связь невладеющей. В стандартной библиотеке для наблюдения за совместно управляемым объектом есть `std::weak_ptr`. В проекте `WeakPtr` отсутствует: сырой наблюдающий указатель допустим только при отдельно обеспеченном времени жизни объекта.

## constexpr и if constexpr

`constexpr` позволяет использовать значение или результат вычисления как константу времени компиляции. Для переменной это означает, что её значение должно быть вычислимо при компиляции:

```cpp
constexpr int size = 10;
constexpr int doubled = size * 2; // Значение 20 известно при компиляции.
```

Для функции `constexpr` разрешает вычисление при компиляции, но не требует его для каждого вызова:

```cpp
#include <iostream>

constexpr int square(int x) {
  return x * x;
}

void example() {
  constexpr int result = square(5); // Вычисление при компиляции.

  int number;
  std::cin >> number;
  int runtimeResult = square(number); // Значение зависит от ввода.
}
```

`const` означает запрет изменения переменной, но её значение может быть получено при запуске. Например, `const int value = readNumber();` допустимо для обычной функции ввода, а `constexpr int value = readNumber();` — нет, если результат нельзя вычислить при компиляции.

`if constexpr` выбирает ветвь при компиляции. В указателях используется такая проверка:

```cpp
if constexpr (
  !std::is_same_v<std::remove_cv_t<U>, std::remove_cv_t<T>>
) {
  static_assert(
    std::has_virtual_destructor_v<T>,
    "Базовый тип должен иметь виртуальный деструктор"
  );
}
```

Если типы совпадают без учёта `const` и `volatile`, проверка виртуального деструктора не нужна. Если различаются — она выполняется при компиляции.

При инстанцировании шаблона отброшенная ветвь `if constexpr` не инстанцируется. Обычный `if` такого свойства не имеет: обе ветви участвуют в проверке шаблона, даже когда условие заранее известно. Например, с обычным `if` проверка виртуального деструктора в этом коде сработала бы и для `int`. При этом `if constexpr` не позволяет помещать в отброшенную ветвь произвольный синтаксически неверный код.

## std::remove_cv_t и std::is_same_v

Оба средства объявлены в `<type_traits>` и работают с типами при компиляции.

`std::remove_cv_t<T>` даёт тип без верхнеуровневых квалификаторов `const` и `volatile`:

| Исходный тип | Результат |
|---|---|
| `const int` | `int` |
| `volatile int` | `int` |
| `const volatile int` | `int` |
| `int` | `int` |

Это преобразование типа, а не изменение объекта или снятие защиты с существующего значения. Квалификаторы вложенных типов не удаляются: `std::remove_cv_t<const int*>` остаётся `const int*`, поскольку `const` относится к объекту по адресу, а не к самому указателю.

`std::is_same_v<A, B>` возвращает константу `true`, если типы одинаковы, иначе `false`:

```cpp
static_assert(std::is_same_v<int, int>);
static_assert(!std::is_same_v<int, double>);
static_assert(!std::is_same_v<int, const int>);
```

В выражении `std::is_same_v<std::remove_cv_t<U>, std::remove_cv_t<T>>` сначала убираются квалификаторы обоих типов, затем сравниваются результаты.

```cpp
UniquePtr<const int> pointer(new int(42));
```

Здесь исходный тип `U` — `int`, тип владельца `T` — `const int`. После преобразования оба равны `int`, поэтому виртуальный деструктор не требуется. Для `U = Derived` и `T = Base` типы остаются разными и включается соответствующая проверка.

Удаление `const` при сравнении типов не разрешает изменять константный объект. Отдельная проверка `std::is_convertible_v<U*, T*>` запрещает передачу `const int*` владельцу изменяемого `int`.

## static_assert в этой реализации

`static_assert` проверяет условие при компиляции. В указателях проверки находятся внутри шаблонных методов и срабатывают при инстанцировании их тел.

Проверяются совместимость указателей, наличие виртуального деструктора при смене типа объекта и совместимость массивов. Проверка не выполняется во время работы программы и не определяет, как фактически была выделена память.

В отличие от ограничения `requires`, утверждение в теле не исключает функцию из набора кандидатов. Поэтому проверка одной сигнатуры через `std::is_constructible` может дать `true` для операции, фактический вызов которой не скомпилируется.

## Типичные ошибки

| Ошибка | Последствие или правильное действие |
|---|---|
| `delete owner.get()` | Владелец сохраняет адрес; позже возможен повторный `delete` |
| Создание второго владельца из `first.get()` | Возникают независимые группы владения; копировать нужно сам `SharedPtr` |
| Забыто удаление после `release()` | Утечка ресурса |
| Доступ через наблюдателя после уничтожения последнего владельца | Обращение к объекту с закончившимся временем жизни |
| Разыменование пустого указателя | Неопределённое поведение, исключение не предусмотрено |
| Использование объекта-владельца для массива | Неправильная форма удаления |
| Выход за границы `operator[]` | Неопределённое поведение |
| Цикл из `SharedPtr` | Ресурсы сохраняются без внешних владельцев |
| Использование `std::move` как доказательства перемещения | Фактическое поведение определяется выбранной операцией |
