# План реализации MiniLang на C++

Основание: [техническое задание](specification.md). Этапы выполняются последовательно; расширения языка начинаются после приёмки базовой версии. Этот документ описывает будущую работу, отметки ниже пока не означают выполненные этапы.

## Этап 1. Проверить структуры данных и зафиксировать контракты

- [ ] Изучить текущие заготовки в `interpreter/`, интерфейсы контейнеров и конфигурацию CMake.
- [ ] Проверить `Array<Token>`, `Map<std::string, Value>` и выбранный контейнер инструкций на реальных предполагаемых типах.
- [ ] Проверить хранение некопируемых `UniquePtr`: добавление, перераспределение памяти, перемещение, уничтожение.
- [ ] При необходимости минимально доработать контейнер инструкций для перемещения элементов; не заменять собственные контейнеры стандартными ради обхода ограничения.
- [ ] Зафиксировать правила числового вывода, ошибки и синтаксис идентификаторов в соответствии с ТЗ.
- [ ] Зафиксировать `Stack<CallFrame>` как будущий стек вызовов; запланировать доработки `top` и `push` перед этапом функций. Они не блокируют первую версию без функций.

Результат: выбран способ хранения токенов, инструкций и узлов; известны необходимые изменения контейнеров.

Проверки: тесты добавления элементов сверх исходной ёмкости, сохранения порядка и значений, единственного уничтожения объектов; существующие тесты затронутых контейнеров. Критерий готовности — структуры поддерживают предполагаемые типы без копирования владельцев и потери данных.

## Этап 2. Создать основу модуля и модель ошибок

- [ ] Выделить независимый от Qt модуль интерпретатора и тесты `tests/Interpreter/`.
- [ ] Ввести типы токенов и `Token` с полями `type` и `lexeme`; диагностику с этапом и описанием причины. Координаты отложены до отдельной доработки.
- [ ] Ввести `Value` для числа и логического значения, определить форматирование.
- [ ] Подключить новые исходники и тесты к CMake, сохранив существующие цели.

Результат: компилируемый каркас с общими типами. Проверки — форматирование обоих типов значений, содержание диагностик, сборка без Qt.

## Этап 3. Реализовать лексер

- [ ] Преобразовывать текст в `Array<Token>` с завершающим EOF.
- [ ] Поддержать целочисленные литералы, идентификаторы, `remember`, `print`, операторы, скобки и переводы строк.
- [ ] Распознавать двухсимвольные операторы раньше односимвольных.
- [ ] Считать CRLF одним переводом строки; координаты токенов и EOF пока не хранить.
- [ ] Завершать анализ понятной ошибкой на неподдерживаемом символе. Будущие ключевые слова, если зарезервированы, не должны создавать впечатление реализованных инструкций.

Результат: корректная последовательность токенов без построения AST.

Проверки: каждый вид токена, ключевое слово внутри более длинного имени, пустой ввод, пробелы, LF/CRLF, EOF после оператора и недопустимые символы.

## Этап 4. Реализовать AST и владение узлами

- [ ] Ввести выражения: число, имя, бинарная операция.
- [ ] Ввести инструкции: сохранение переменной и вывод.
- [ ] Хранить программу в собственном последовательном контейнере, а дочерние узлы — через `UniquePtr`.
- [ ] Предусмотреть последующее добавление координат для диагностик выполнения; сейчас узлы AST их не хранят.
- [ ] Обеспечить безопасное уничтожение полиморфных объектов и частично построенного дерева.

Результат: AST можно собрать вручную без лексера и парсера. Проверки — создание и уничтожение вложенного дерева с подсчётом разрушенных узлов; перемещение программы без копирования владельцев.

## Этап 5. Реализовать парсер выражений

- [ ] Применить рекурсивный спуск по уровням: первичные выражения, умножение, сложение, сравнение, равенство.
- [ ] Обрабатывать скобки и левую ассоциативность.
- [ ] Проверять границы последовательности и обрабатывать EOF без обращения за пределы контейнера.
- [ ] Сообщать о пропущенных операндах и скобках с описанием причины без координат.

Результат: выражение преобразуется в AST с правильной структурой.

Проверки структуры: `2 + 3 * 4`, `(2 + 3) * 4`, `10 - 3 - 2`, `20 / 5 / 2`, сочетания сравнений и равенства. Ошибки: пустые скобки, незакрытая скобка, оператор без правого операнда. Проверки не должны зависеть от ещё не написанного исполнителя.

## Этап 6. Реализовать разбор программы

- [ ] Разбирать `remember имя = выражение` и `print выражение`.
- [ ] Пропускать пустые строки, принимать EOF сразу после последней инструкции.
- [ ] Запрещать лишние токены и две инструкции на одной строке.
- [ ] Возвращать готовую программу только после успешного разбора всего ввода.

Результат: полный исходный текст преобразуется в программу AST.

Проверки: несколько инструкций, пустой файл, LF/CRLF, отсутствие завершающей новой строки; пропущенное имя или `=`, лишние токены, неподдерживаемая инструкция. Проверить освобождение уже построенных инструкций при ошибке в последующей.

## Этап 7. Реализовать окружение на красно-чёрном дереве

- [ ] Обернуть `Map<std::string, Value>` интерфейсом поиска и сохранения переменной.
- [ ] Использовать `containsKey`, `insert`, `replace` и `at` с учётом фактических контрактов дерева.
- [ ] Преобразовывать отсутствие имени в диагностику языка.
- [ ] Создавать новое окружение для независимого выполнения программы.

Результат: окружение хранит оба типа значений и обновляет существующий ключ без дублирования.

Проверки: добавление, обновление, отсутствующее имя, регистр имён, сохранение логического результата, большое число переменных с последующим чтением всех значений.

## Этап 8. Реализовать вычисление и выполнение

- [ ] Вычислять узлы AST с проверкой типов и порядком слева направо.
- [ ] Поддержать арифметику, сравнения и ошибку деления на ноль.
- [ ] Сначала вычислять правую часть `remember`, затем изменять окружение.
- [ ] Последовательно выполнять инструкции, выводить через переданный поток.
- [ ] Останавливать выполнение на первой ошибке, сохраняя ранее произведённый вывод.

Результат: программы выполняются через программный интерфейс без CLI.

Проверки: контрольная программа из ТЗ; все операторы, дробный результат деления, использование старого значения при перезаписи, неверные типы, неизвестное имя, независимые запуски. При ошибке в правой части значение существующей переменной не должно изменяться.

## Этап 9. Подключить CLI

- [ ] Создать цель `MiniLangCpp`, принимающую один путь к файлу.
- [ ] Обрабатывать отсутствие аргумента, лишние аргументы и ошибки чтения.
- [ ] Последовательно запускать лексер, парсер и исполнитель.
- [ ] Разделить стандартный вывод и диагностику, возвращать корректные коды завершения.
- [ ] Добавить примеры `.mini` и инструкцию по сборке и запуску.

Результат: файл выполняется командой `MiniLangCpp path/to/program.mini`.

Проверки: успешный файл, отсутствующий файл, ошибочные аргументы и ошибки каждого этапа. Ошибка в конце разбираемого файла не должна приводить к выполнению его начальных инструкций.

## Этап 10. Провести приёмку базовой версии

- [ ] Сопоставить реализацию со всеми требованиями ТЗ и автоматизировать сквозные сценарии.
- [ ] Проверить безопасность памяти, включая частично построенное AST и ошибки выполнения, при доступности инструментов — с AddressSanitizer/UndefinedBehaviorSanitizer.
- [ ] Собрать проект и выполнить CTest, проверить существующие цели и тесты.
- [ ] Проверить сборку интерпретатора с `BUILD_GUI=OFF`.
- [ ] Зафиксировать фактические результаты, ограничения и отличия от изученной Java-версии.

Основные команды из корня репозитория:

```bash
cmake -S . -B /tmp/ds-build -DCMAKE_BUILD_TYPE=Release -DBUILD_GUI=ON
cmake --build /tmp/ds-build --parallel 2
ctest --test-dir /tmp/ds-build --output-on-failure
```

Для независимой проверки без GUI конфигурацию повторяют с `-DBUILD_GUI=OFF`. При недоступности Qt GUI-проверку отмечают как пропущенную; успешная консольная сборка её не заменяет.

Критерий готовности: все обязательные сценарии проходят, основной путь использует собственные контейнеры, существующие проверки не регрессировали, команды запуска и ограничения документированы.

## Этап 11. Расширять язык отдельными итерациями

Отдельная будущая доработка диагностики: добавить `line` и `column` в `Token`, отслеживать их в лексере (включая LF/CRLF и EOF), передавать положение в AST и включать его в ошибки всех этапов. Добавить тесты координат с нумерацией от единицы. Эта доработка не блокирует базовую версию.

Каждая итерация начинается с уточнения ТЗ и примеров, затем охватывает токены, AST, парсер, исполнитель и тесты.

1. Дробные литералы и унарные операции: определить форму литералов и приоритет унарных операторов.
2. Строки: определить экранирование, допустимые операции и формат вывода.
3. `when … otherwise`: определить синтаксис блоков и требования к типу условия.
4. `repeat`: определить условие или число повторений, порядок проверок и правила завершения.
5. Области видимости: определить поиск, затенение и присваивание; подключить `Stack` окружений с учётом некопируемого `Map`.
6. Функции: определить параметры, возврат и рекурсию; ввести перемещаемый некопируемый `CallFrame` и стек вызовов `Stack<CallFrame>`. До подключения кадров выполнить доработки стека и проверки ниже.

### Подготовка Stack к кадрам вызовов

- [ ] Заменить `T top() const` перегрузками `T& top()` и `const T& top() const`, чтобы получать текущий кадр без копирования.
- [ ] Реализовать `push(T&& value)` с перемещением значения через конструктор узла в `data`; сохранить `push(const T& value)` для копируемых lvalue.
- [ ] Проверить всю цепочку создания узла: некопируемый кадр не должен копироваться ни в аргументах, ни при инициализации поля.
- [ ] Определить поведение `top` и `pop` на пустом стеке, описать время жизни ссылок на вершину.
- [ ] Добавить тесты в `tests/Stack/` с перемещаемым некопируемым типом: `push(std::move(frame))`, изменение через `top()`, чтение через константный стек, LIFO, уничтожение ресурсов при `pop` и уничтожении стека. Сохранить проверки добавления копируемого lvalue.
- [ ] Подключить `Stack<CallFrame>`: вызов добавляет кадр, возврат удаляет кадр, ошибка освобождает активные кадры без утечек. Проверить вложенные вызовы и рекурсию с раздельными окружениями.

Критерий готовности: кадр с некопируемым окружением проходит полный цикл вызова без копирования; текущий кадр доступен по ссылке, ресурсы освобождаются однократно, тесты стека и функций проходят. `Array` используется для последовательностей, а стек вызовов реализован через `Stack`.

Результат каждой итерации принимается отдельно. Строки, циклы, функции и области видимости не являются условиями готовности первой версии.
